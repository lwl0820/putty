### R1：释放核心后仍可能新增回调，当前清理顺序不完整

- 严重程度：高，生命周期契约错误。
- 位置：`design.md:37`，最后一句“关闭或重用资源先撤销通知与排队事件，再释放核心对象”。对应 `implement.md:23` 仅概括“事件/资源撤销”，没有补足最终清扫。
- 已有证据：`research/terminal-architecture.md` 的生命周期段引用 `vendor/putty/unix/window.c:2503` 至 `:2511`：最后才调用 delete_callbacks_for_context，因为关闭 Backend 等清理操作自身仍可能产生新的顶层回调。`terminal/terminal.c:2150` 至 `:2151` 也说明各核心对象自己有计时与回调清理责任。
- 问题：若按现有一句话的顺序实现“先删全部排队事件，随后 free 核心”，free 期间新增宿主回调可能保留到下一轮，引用已释放对象；仅有初次撤销不能保证关闭完整。资源关闭与 socket 重用也不能完全采用同一套单阶段先删逻辑。
- 建议：明确两阶段清理：先进入 closing、停止新请求/外部输入及产生新动作的通知，拒绝/取消在途用户请求；随后在唯一核心线程释放 Ldisc/Backend/Terminal 等对象，各对象履行内部计时/回调清理；最后再次清除宿主上下文的顶层回调、桥消息和排队 Qt 事件，撤销剩余通知并使宿主代次失效，然后释放宿主。异步请求持有对象须延后到回执完成/已拒绝；不能强杀长 KDF/GSS。socket 重用仍保留原版 moribund 过滤。
- 是否阻碍最终评审：是，需在设计中消除这一清理顺序歧义；这是规划文字修订，不要求当前实现。

### R2：终端矩阵编号与来源不一致

- 严重程度：中，验收追踪引用错误。
- 位置：`design.md:79` 使用“终端 T01–T22”；`implement.md:41` 使用“T01–T22”。
- 已有证据：`research/terminal-parity.md` 的实际编号是 `PT-01` 至 `PT-22`。
- 问题：PRD AC11 要求父子任务及实际结果可追溯，当前正式设计/实施引用不存在的矩阵编号，后续子任务可能继续复制错误 ID。
- 建议：父子文档统一使用 PT-01–PT-22；如选择重命名研究矩阵，则同时全部修订，不建立未说明的第二套别名。Pageant P/I 与 CLI C 编号保持各自已有来源。
- 是否阻碍最终评审：是，作为材料一致性门的小修复；无需扩大任务或重新询问产品范围。

### R3：Windows Pageant 的同步旧 IPC 线程边界建议显式落入子任务

- 严重程度：中，建议补强；当前不是确定性冲突。
- 位置：`design.md:37` 的核心线程 Windows 消息桥、`:61` 的 Pageant 隐藏兼容窗口、`:69` 的在途口令/请求验证。
- 已有证据：`research/pageant-architecture.md:49` 起已说明原版专用 IPC 线程通过事件交接 SendMessage/WM_COPYDATA，核心异步排队请求；函数返回不等于签名完成。已有研究建议保留此边界。
- 建议：Pageant 子任务必须写明同步 WM_COPYDATA 的窗口/等待者独立于唯一核心执行线程，不能在核心线程的 WndProc 等待同一核心队列产出回复；关闭时先失败请求并唤醒 IPC 等待者。唯一“核心所有者线程”不等于进程只能有一个辅助线程。Windows 网络隐藏 HWND 与 Pageant 旧 IPC HWND 的职责分别定义。
- 是否阻碍最终评审：否。现有设计未禁止专用 IPC 线程，研究也已给出可行模式；在 Pageant 子计划中明确即可。

### R4：Windows 测试隔离应覆盖注册表之外的随机种子与子进程

- 严重程度：中，建议补强；已有隔离验证门可容纳。
- 位置：`prd.md:25`、`design.md:77`、`implement.md:22`、`:64`。
- 已有证据：`research/terminal-architecture.md` 说明原版 Windows storage 使用 HKCU，但随机种子另有路径选择；`research/build-cli.md:32` 区分原版测试身份与自有进程临时 hive。
- 建议：共享基础的隔离门验证每个原版/自有子进程实际生效的 HKCU、随机种子、socket/管道、配置、运行时和日志根。不能假定父进程 RegOverridePredefKey 自动隔离未经适配的原版可执行文件；独立测试身份也仍需将开发临时产物重定向到项目 .tmp/。先验证隔离探针，再运行会话/主机密钥写入和代理测试。
- 是否阻碍最终评审：否。设计已有“验证过的”隔离及不使用真实个人配置的硬约束，实施任务须把验证结果落实，未指定全部实现细节本身不构成规划错误。

### R5：早期验证门与响应性承诺可自洽，关闭硬上界需保持明确区分

- 严重程度：说明，无需修订范围。
- 位置：`prd.md:33`；`design.md:69` 至 `:73`；`implement.md:37`、`:43`。
- 判断：GUI 心跳有明确内部阈值；核心线程同步 KDF/GSS 不会因分线程就变得可取消，但设计明确 GUI 继续响应、异步显示关闭状态且不承诺硬取消时限，必要时回到进程隔离/异步补丁评审。两者不矛盾。不得在后续实施将“取消已显示”误记成“核心操作已经终止”。
- 是否阻碍最终评审：否。应保留长同步操作中重绘、取消状态、延迟清理、过期帧与回执的用例，不需要规划阶段提前给出原生平台通过证据。

### 已确认有效的阶段门

1. 用户批准产品范围与最终实施方案分开，父任务维持协调角色，启动具体子任务。
2. 完整运行时与 pg-putty 隔离，CLI-only/全部关闭不找 Qt；没有继承密钥工具裁剪来冒充完整客户端。
3. Qt 终端在铺开 UI 前验证同步字宽、字体回退/DPI、真实网络、KDF/GSS、双平台线程和 GUI 响应性；失败回到设计，不删功能。
4. 原版与新程序双向互操作，旧 IPC 单独测，离屏/原生桌面/发布包证据分开。
5. 原版存储和字体格式保留，未知字段和原版代码页边界不扩大承诺；取消与草稿、动态控件 id/刷新顺序已有契约。
