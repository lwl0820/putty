# 套件运行时与异步生命周期契约

## 1. 范围与触发

适用于 `libs/putty-runtime/`、各产品的 `pr_module` 实现及上游平台事件桥。该规范来自已落地的 C/Qt 运行时及 Linux 回归，Windows 原生 HWND/HANDLE、实际认证和终端绘制仍需各任务独立验证。

## 2. 接口与所有权

`putty_runtime/core.h` 只暴露自有不透明句柄、命令、事件和状态。模块的 `create/command/destroy/drained`、上游对象及 `pr_core_*` 入口均由唯一核心线程调用。Qt 门面 `Runtime` 排队提交输入、发出事件并异步关闭，不向 GUI 暴露 `Conf`、`Terminal` 或 `Backend`。

进程内只允许一个活动核心，第二个返回 `PR_BUSY`。模块自行管理自己的全部上游子对象；客户端模块管理 PRNG，通用运行时及 Pageant 模块不能初始化客户端 PRNG。字节指针只在当前 C 调用期间有效，跨队列须在容量检查成功后复制。

## 3. 队列与请求

- 每个命令携带 `generation/object_id/request_id`；跨代命令返回 `PR_STALE`，关闭后的输入返回 `PR_CLOSING`。
- 一次性请求先用 `pr_core_request` 登记，再发布事件；回复核对所属对象，重复或过期回复不能再执行完成器。关闭撤销未完成请求。
- 命令和事件同时限制条数及总字节，满时明确返回 `PR_BACKPRESSURE`。调用者保留尚未接受的输入，容量恢复后重试，不能把拒绝当成功。
- 普通事件为命令完成预留一个槽。事件发布必须在同一受锁分支先检查单条大小与剩余额度，再读取调用者缓冲区、复制并入队；不能先构造大 `QByteArray` 再拒绝。
- 唤醒只保留一个排队项，顶层回调按预算执行。事件消费者释放容量后调用模块 `drained`；状态快照合并策略由产品模块另行定义，不能无界追加帧。
- 命令和启动选项临时字节使用后清零；事件只包含前端需要的状态，不携带私钥、口令或解密材料。

## 4. 平台事件与代次

Unix fd 通知携带注册编号，重新注册相同 fd 也产生新身份。处理异常、读、写前逐次核对关闭状态、身份及当前兴趣；任何回调发起关闭后，同批后续通知立即停止。整个 fd 分发计入 `dispatch_depth`，保证回调中只能发起关闭，不能直接销毁核心。读通知抵达时探测 OOB，保持异常在读之前。撤销通知器先禁用，再延后释放。

Windows 网络保留原版 `WSAAsyncSelect`、隐藏窗口、`winselgui_response` 和顶层回调路径。HANDLE 等待的身份是 `{handle, registration}`，不能只比较数值、树索引或分配地址。上游等待快照保存不可复用的注册编号；激活先查当前注册再比对，不能解引用旧等待对象。Qt 撤销旧代次通知器，C 边界再次核对。实际 OS 句柄、消息循环和手动/自动复位语义仍由原生 Windows 用例确认。

计时器使用上游绝对 tick，转换等待间隔时保留原宽度的回绕语义；不把绝对 tick 直接当作毫秒延迟。

## 5. 关闭与失败案例

正常：GUI 调用 `close()`，立即停止接受输入；核心抵达安全点后撤销外部通知、取消请求、析构模块，再清扫析构过程中新增的回调、计时及桥消息，最后释放核心。

边界：模块回调中可调用 `pr_core_begin_close`，不能在该栈内调用 `pr_core_destroy`。Qt 门面析构不 `join/wait` 核心；独立共享状态完成收尾。发事件的槽可删除门面，发出每个事件后必须核对 `QPointer` 再继续访问对象。

错误：用旧 HANDLE 激活新等待项；GUI 等待正在执行同步认证的核心；模块析构前只删除一遍回调；事件超限时仍读取其 payload。这些都破坏运行时边界，即使普通连接用例通过也不能接受。

## 6. 必需验证

`runtime-lifecycle` 覆盖真实双向 TCP、背压恢复、OOB、断开重开、一次性请求、回调/计时取消、析构新增回调、异步关闭和槽内删除；超额事件用不可读内存探针证明拒绝发生在读取前。

Unix 内联 OOB 的 `urgent=1` 标记紧急位置之前的数据，不是紧急字节本身。测试须分别控制前置数据已经读空和仍待处理两种状态；不能无条件以该标记判断紧急字节是否送达。异常先于读取的契约另用真实 TCP 同时 R／PRI 就绪、非内联 `MSG_OOB` 字节及普通流精确比较验证。

`runtime-handle-registration` 在 Linux 以窄平台类型 shim 编译真实 Windows 等待算法，覆盖旧快照、同值复用和回调中注销。它不能替代 Windows 原生通知测试。`runtime-core-link` 与 `runtime-agent-core-link` 分别验证完整客户端及代理的实际链接闭包和初始化。

运行测试前使用项目 `.tmp/` 隔离原版存储、种子、临时路径与代理环境；没有逐进程 HKCU 隔离的 Windows runner 明确跳过，不能修改个人注册表来获得通过。没有对应依赖或平台的跳过必须列入报告。

## 7. 正确做法示例

发布事件：持队列锁 → 验证 `size` 和剩余条数/字节 → 复制 payload → 入队 → 安排一次唤醒。过限分支只返回 `PR_BACKPRESSURE`，不触碰 payload。

处理等待：快照保留 `registration` → 通知器捕获同一身份 → C 层核对仍为当前注册 → 调用上游激活。撤销和同值重建后的旧通知均无效。
